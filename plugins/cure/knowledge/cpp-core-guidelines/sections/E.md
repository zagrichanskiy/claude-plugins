# E (Error handling)

Condensed from C++ Core Guidelines commit 33bcd015997f0d8e0fa0202eb66254a16f59ad8f: rule id, title, reason, and a search hint where one exists.
Generated by scripts/condense-core-guidelines.py. Do not edit.

## E.1: Develop an error-handling strategy early in a design

A consistent and complete strategy for handling errors and resource leaks is hard to retrofit into a system.

## E.2: Throw an exception to signal that a function can't perform its assigned task

To make error handling systematic, robust, and non-repetitive.

## E.3: Use exceptions for error handling only

To keep error handling separated from "ordinary code."
C++ implementations tend to be optimized based on the assumption that exceptions are rare.

## E.4: Design your error-handling strategy around invariants

To use an object it must be in a valid state (defined formally or informally by an invariant) and to recover from an error every object not destroyed must be in a valid state.

Search hint: `grep -nE '\bthrow\b|\.at\(|\bsto(i|l|ul|ll|ull|f|d|ld)\(|\bnew\b|\.(push_back|emplace_back|emplace|insert|resize|reserve)\(' <files>` lists direct throws and common throwing calls (bounds-checked access, string conversion, allocation). A throwing call is also any call not declared `noexcept` whose contract says it throws: check the callee's documentation (`\throws`, `@throws`) or its body, at any depth. Then sweep the callers: for each function that contains a `throw` or a throwing call, grep its callers (`grep -rnE '\b<function>\s*(<[^>]*>)?\('`) and treat each calling function as a hit; repeat one level up while the caller does not catch. In each function that is a hit, list the assignments (`[^=!<>]=[^=]`) that precede the throw or the throwing call to members (`this->`, or a name declared in the class, for example under an `m_` prefix or a `_` suffix), out-parameters (a dereferenced pointer or a non-const reference parameter) and globals. Include writes through a local reference or pointer bound to that state (`auto& v = <member or parameter>...; v.f = ...;`). Each write is visible to the caller after the throw unless the function restores it.

## E.5: Let a constructor establish an invariant, and throw if it cannot

Leaving an object without its invariant established is asking for trouble.
Not all member functions can be called.

## E.6: Use RAII to prevent leaks

Leaks are typically unacceptable.
Manual resource release is error-prone.
RAII ("Resource Acquisition Is Initialization") is the simplest, most systematic way of preventing leaks.

Search hint: `grep -nE '\bnew\b|\b(malloc|fopen|open|openat|shm_open|mmap|socket|accept4?|dup2?|pipe2?|eventfd|timerfd_create|epoll_create1?|opendir|pthread_mutex_lock)\(|\.lock\(\)' <files>` lists raw acquisitions whose release is a separate statement.

## E.12: Use `noexcept` when exiting a function because of a `throw` is impossible or unacceptable

To make error handling systematic, robust, and efficient.

Search hint: `grep -nE 'extern\s+"C"|\bmain\s*\(|std::j?thread|pthread_create|\bsignal\s*\(|sigaction' <files>` lists C-linkage functions, `main`, thread entry points and signal handlers; a throw must not leave any of them or the function a thread or C caller runs. Move constructors, move assignments and `swap` are C.66 and C.85, checked by `cg-classes`.

## E.13: Never throw while being the direct owner of an object

That would be a leak.

Search hint: `grep -nE '\bnew\b|\bmalloc\(' <files>`; in each function, a `throw` or a throwing call between the allocation and the hand-over to an owner leaks it.

## E.14: Use purpose-designed user-defined types as exceptions (not built-in types)

A user-defined type can better transmit information about an error to a handler.  Information
can be encoded into the type itself and the type is unlikely to clash with other people's exceptions.

Search hint: `grep -nE '\bthrow\s+([0-9"-]|std::string\b)' <files>` lists built-in types and strings thrown.

## E.15: Throw by value, catch exceptions from a hierarchy by reference

Throwing by value (not by pointer) and catching by reference prevents copying, especially slicing base subobjects.

Search hint: `grep -nE '\bthrow\s+new\b|\bcatch\s*\(\s*(const\s+)?[A-Za-z_:<>]+(\s+\w+)?\s*\)' <files>` lists pointers thrown and exceptions caught by value.

## E.16: Destructors, deallocation, `swap`, and exception type copy/move construction must never fail

We don't know how to write reliable programs if a destructor, a swap, a memory deallocation, or attempting to copy/move-construct an exception object fails; that is, if it exits by an exception or simply doesn't perform its required action.

Search hint: `grep -nE '~\w+\s*\(|\bswap\s*\(|noexcept\s*\(\s*false\s*\)' <files>` lists destructors, `swap` and `noexcept(false)`; check each body for a `throw` or a throwing call outside a `try`.

## E.17: Don't try to catch every exception in every function

Catching an exception in a function that cannot take a meaningful recovery action leads to complexity and waste.
Let an exception propagate until it reaches a function that can handle it.
Let cleanup actions on the unwinding path be handled by RAII.

Search hint: `grep -nE '\bcatch\s*\(\s*(\.\.\.|(const\s+)?std::exception\b)' <files>` lists catch-all handlers; check that each function can recover.

## E.18: Minimize the use of explicit `try`/`catch`

 `try`/`catch` is verbose and non-trivial uses are error-prone.
 `try`/`catch` can be a sign of unsystematic and/or low-level resource management or error handling.

Search hint: `grep -nE '\btry\b' <files>` lists the explicit `try` blocks.

## E.19: Use a `final_action` object to express cleanup if no suitable resource handle is available

`finally` from the GSL is less verbose and harder to get wrong than `try`/`catch`.

Search hint: `grep -nE '^\s*throw\s*;' <files>` lists rethrows; a handler that cleans up and rethrows is a `final_action` candidate.

## E.25: If you can't throw exceptions, simulate RAII for resource management

Even without exceptions, RAII is usually the best and most systematic way of dealing with resources.

## E.26: If you can't throw exceptions, consider failing fast

If you can't do a good job at recovering, at least you can get out before too much consequential damage is done.

**See also**: Simulating RAII

## E.27: If you can't throw exceptions, use error codes systematically

Systematic use of any error-handling strategy minimizes the chance of forgetting to handle an error.

**See also**: Simulating RAII

## E.28: Avoid error handling based on global state (e.g. `errno`)

Global state is hard to manage and it is easy to forget to check it.
When did you last test the return value of `printf()`?

**See also**: Simulating RAII

Search hint: `grep -nE '\berrno\b' <files>` lists error handling through `errno`.

## E.30: Don't use exception specifications

Exception specifications make error handling brittle, impose a run-time cost, and have been removed from the C++ standard.

Search hint: `grep -nE '\)\s*(const\s*)?throw\s*\(' <files>` lists dynamic exception specifications.

## E.31: Properly order your `catch`-clauses

`catch`-clauses are evaluated in the order they appear and one clause can hide another.

Search hint: `grep -nE '\bcatch\s*\(' <files>` lists the handlers; in each sequence, a base type caught before a type derived from it hides the derived handler.
